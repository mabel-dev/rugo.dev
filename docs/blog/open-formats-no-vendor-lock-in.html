Bye-bye vendor lock-in: a data stack made of open files and 13.5 MB of open-source Python

Justin Joyce · 21 October 2026 · 7 min read

Correct at time of publishing. For up-to-date performance and feature information, see rugo.dev.

Lock-in isn't the logo on the invoice. It's the file format your data sits in and the engine that's the only thing able to read it. Keep your data in Parquet, Avro and JSON Lines, read it with an open-source library that takes 5.4% of a Lambda package, and every vendor in your stack becomes optional.

Platforms like Databricks and Snowflake are good at what they do, and for a lot of teams they're the right call. The trouble starts later, when the bill grows with usage in ways that are hard to forecast, and moving anything out means rewriting everything that touches it. Nobody chose that on day one. It accumulated.

The way out isn't a heroic migration. It's a handful of small decisions, made early, that keep the exit door unlocked. This post is the blueprint: what to keep open, what a minimal stack looks like, what it costs to run, and where a bigger engine plugs in when you need one.

Where lock-in actually lives

There are three places a platform can hold on to you, and only the first two are really about the vendor.

  • The storage format. If your tables live in a proprietary layout, only that vendor's engine can read them. Export is a project.
  • The metadata. Catalogs, permissions and job definitions that exist only inside one product. You can rebuild these, but it takes time.
  • The code. SQL dialects, proprietary functions and notebooks that call vendor APIs. This is the one you control completely, and it's the part that's cheapest to keep portable.

The first is the one that matters most, and it's also the easiest to fix. If your data is in an open file format in a bucket you own, anything can read it: today's engine, tomorrow's engine, a script you write on a Friday. The format is the contract, and nobody can put a price on it.

The three files that cover almost everything

You don't need a long list of formats. Three open ones cover nearly every pipeline, and each is good at one job. We opened the same 4,630 rows in all three in Avro vs Parquet vs JSON Lines:

Format Same 4,630 rows Use it for
JSON Lines 1.09 MB Logs and API exports. Anything can write it.
Avro 113 KB Streams and event pipelines, written one record at a time.
Parquet 93 KB Analytics. Readers skip columns and whole row groups.

All three are open specifications with readers in every major language. Land raw data as JSON Lines or Avro, keep the curated tables as Parquet, and you've covered the whole path from ingest to analysis without a single proprietary byte.

The stack, piece by piece

Here's what each job in a managed platform looks like when you build it from open parts. Every row has more than one good answer, which is exactly the point.

Job Open building block Why it stays swappable
Storage Object storage (S3 or any compatible store) It's just files in a bucket you own
Table format Parquet, Avro, JSON Lines Open specs, many readers
Small and mid-size reads rugo in a Lambda or a container Apache 2.0, 13.5 MB, no dependencies
Heavy SQL and joins DuckDB, Spark or Opteryx over the same files They read the same Parquet
Orchestration Airflow, EventBridge, cron, anything A scheduler holds no data

The middle rows are where the money goes, so they're where we'll spend the rest of the post.

What the compute layer costs

A lot of what a warehouse is used for is unglamorous: read a file as it lands, check it, filter it, compute a number, write a smaller file. That doesn't need a cluster. It needs a function that starts quickly and reads efficiently, and that's what you pay for on Lambda: every millisecond of start-up and every millisecond of reading.

This is what a Parquet reader costs to ship to Lambda, measured by building each package the way Lambda does (full write-up):

Library Unzipped Of the 250 MB limit Direct upload?
rugo 0.5.4 13.5 MB 5.4% yes
duckdb 1.5.6 61.7 MB 24.7% yes
pyarrow 26.0.0 172.5 MB 69.0% no
polars 2.0.0 196.3 MB 78.5% no

A small package means a fast start, and on Lambda a fast start is money. rugo starts 1.5 to 2.2 times faster than PyArrow, DuckDB or Polars, and in our cost comparison it came out 15% to 35% cheaper than PyArrow in every configuration we ran. At 1024 MB on x86 it was the cheapest of all four once about one call in ten was a cold start.

In absolute terms the bill is small. Reading most of a 38.6 MB Parquet file on every call, a million calls cost $2.33 when every call is warm and $22.70 when every call is cold, requests included. That's the whole price of the compute. There's no cluster to size, nothing idling overnight, and the meter stops when the function does.

rugo is open source too, under the Apache 2.0 licence. The code that reads your files is as open as the files themselves: you can read it, fork it and run it anywhere, with no licence server and no per-seat or per-query meter. That's the other half of keeping the exit unlocked.

The pipeline, in code

Here's a landing step that turns a raw JSON Lines drop into Parquet. It uses the same two calls whether it runs on your laptop, in a container or in a Lambda: 

from rugo import jsonl, parquet

with jsonl.read_jsonl("events.jsonl") as reader:
    with open("events.parquet", "wb") as f:
        with parquet.open_parquet_writer(f.write) as writer:
            for morsel in reader:
                writer.write_row_group(morsel)

And here's the read side, pulling only the columns and rows a question needs: 

from rugo import parquet

with parquet.read_parquet(
    "events.parquet",
    columns=["status", "response_ms"],
    predicates=[("status", "==", 200)],
) as reader:
    for morsel in reader:
        print(morsel.num_rows)

There's no session to open, no cluster to attach to and no credentials for a platform. A file goes in and a file comes out, and the Parquet it writes is readable by every engine that exists. The full Lambda handler, including the S3 download and the deployment commands, is in Reading Parquet in AWS Lambda without PyArrow.

It isn't only Parquet

Open formats only help if the readers are good, so the other two are held to the same standard. On a 1 GB JSON Lines log, rugo answered the question in 1.23 seconds with about 5 MB of native overhead, where pandas needed 2,500 MB (the comparison). On Avro, called from Python, it was 2.3 to 4.5 times faster than arrow-avro, Apache Arrow's own Rust reader, on its defaults (the race). Raw landing zones and curated tables get the same treatment, with the same library.

When you want a bigger engine

This is where the open-format choice pays off. Some work does deserve a bigger engine: wide joins across large tables, many analysts running SQL at once, a long tail of ad-hoc exploration. Because your data is plain Parquet in your own bucket, you don't migrate to get that. You point DuckDB, Spark or Opteryx at the same files, and they run alongside the Lambda functions that are already there.

That's the shape of a stack with no lock-in: small functions for the many small jobs, big engines for the few big ones, and one set of files underneath that nobody owns but you. Swapping any component is a configuration change instead of a rewrite.

A short exit-proofing checklist

  • Land raw data as JSON Lines or Avro, in a bucket you control.
  • Store curated tables as Parquet, with row groups sized so readers can skip them.
  • Keep transformations in plain Python and SQL you can run outside any one platform.
  • Keep your orchestration and permissions in code, in your repository.
  • Once a quarter, read a table with a different engine than the one that wrote it. If it works, you're free.
